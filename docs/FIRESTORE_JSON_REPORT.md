# Firestore → JSON → MCP → Gemini: аудит и оптимизация

Дата: 20 октября 2026. Изменения продолжают первоначальную интеграцию Firestore,
не добавляют хранилище, зависимости, deployment или платные сервисы.

## 1. Что уже работало

До этой задачи существовали FirestoreRepository/FirestoreStorage, локальный ключ
и ADC, выбор через CAMPUSPULSE_LMS_REPOSITORY=firestore, восемь LMS-инструментов,
два инструмента личных данных и подписанное подтверждение изменений через API.
Repository возвращал словари/списки, даты нормализовались в Asia/Qyzylorda.
Были ограничения выдачи, изоляция пользователей, проверки владельцев курсов,
транзакционные записи, asyncio.to_thread и снимок чтения на один инструмент.
JSON-файлы уже не являлись промежуточным хранилищем. Предыдущий набор — 97 тестов.

Сохранены эти модели и интерфейсы. `agent.py` уже передавал объект результата
в Gemini `Part.from_function_response`; этот компонент не переписывался.
`lms_repository`, `lms_store`, `lms_data`, `domain` также сохраняют контракты.

## 2. Обнаруженные проблемы

- Общий список курсов выполнял get для каждого курса и повторно читал зачисления.
- Операция одного курса сначала перечисляла все курсы студента.
- query_data получал полный ограниченный список, затем выбирал поля и фильтровал
  в памяти. Даже поиск одного задания не имел адресного пути по id.
- Курсор содержал offset/хеш полного списка; выдача коллекции больше 100 была
  невозможна даже с маленькими страницами.
- План загружал полные description и другие неиспользуемые поля; local предварительно
  вызывал get_assignments, после чего plan_study снова читал задания.
- Аннотация MCP `-> dict` не задавала SDK выходную схему; некоторые результаты
  приходили только JSON-текстом. Клиент уже умел предпочитать structuredContent.
- Ошибки транспорта/валидации и источника имели неодинаковый набор полей.
- Подготовка личного изменения могла включить в before неизвестные поля импортированного
  документа; подписанный proposal также попадал в контекст модели.

## 4. Как проходит запрос

```text
Пользователь → существующий Gemini function-calling loop
             → разрешённый инструмент MCP
             → LmsTools / проверенный actor
             → FirestoreRepository / транзакция чтения
             → FirestoreStorage: where + select + limit / get / get_all
             → публичные поля + ISO 8601 + JSON-совместимый словарь
             → MCP structuredContent → агент → Part.from_function_response
             → ответ Gemini по данным инструмента
```

Модель выбирает только имена ресурсов/полей из разрешённого каталога и equality
фильтры. Raw SDK-команды, произвольные коллекции, student_id/role/actor и владелец
из модельных аргументов недоступны. Идентичность задаётся проверенной сессией.
Проверяются зачисления, архивирование и владение; у адресного чтения зачисления
также проверяется совпадение course_id/student_id с запрошенной областью.

Все десять инструментов сохранены; новых инструментов не добавлено. Для дедлайнов
используются get_assignments или query_data(assignments, fields=[id,title,due]),
для расписания query_data(lessons), для поиска заданий filters.id или точный
filters.title. get_courses читает собственные курсы; get_personal_data — собственные
задачи и настройки. Состав бизнес-полей не переименован: due остаётся due,
done остаётся done; выдуманный status не добавляется.

## 5. JSON-контракт и границы

Сохранены прежние плоские формы результатов, вместо несовместимой новой обёртки
success/data/metadata. Для query_data:

```json
{
  "items": [{"id":"assignment-id","title":"Task","due":"2030-01-01T05:00:00+05:00"}],
  "next_cursor": null,
  "resource": "assignments",
  "source": "firestore:campuspulse-ai-1021/(default)",
  "team_database_connected": true,
  "data_access": []
}
```

Здесь data_access сокращён только в примере; приложение сохраняет фактические
события доступа. get_assignments сохраняет assignments/personal_tasks, план — plan,
пустые наборы представлены списками [], последняя страница — next_cursor=null.
Отсутствующий документ по filters.id даёт пустую выдачу; PATCH по отсутствующему id
по-прежнему даёт 404. Недоступность источника не маскируется пустым списком.

Семантическая ошибка инструмента сохраняет строковый error и числовой status,
дополняя их error_code/retryable:

```json
{"error":"Источник данных недоступен.","status":503,"error_code":"source_unavailable","retryable":true}
```

Обычные ошибки API по-прежнему используют существующий HTTP-контракт. Ошибки
самого MCP-протокола/SDK отдельно могут иметь isError; доменные ошибки читаются
по error/status, включая ранее существовавшую форму 503. Логи драйвера, значения
credentials и исключения произвольных объектов в результат не включаются.

`lms_json` поддерживает aware datetime, date, Enum/IntEnum, UUID, вложенные dict/list.
datetime возвращается с часовым поясом Asia/Qyzylorda; date — ISO calendar date.
Naive datetime, NaN/Infinity, нестроковые ключи и неизвестные SDK-объекты отклоняются.
Не используется небезопасное default=str. Публичные поля определяет Repository;
сериализатор не заменяет авторизацию или allowlist.

Штатный MCP SDK получает аннотацию dict[str, Any], формирует outputSchema и
structuredContent с исходными ключами, без JSON-строки или дополнительного result.
Для старого клиента сохраняется поддержка текстового content. Это соответствует
[структурированным результатам MCP](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content).

Gemini получает словарь, а не сериализованный JSON-текст. В model context нет
data_access и signed proposal. API сохраняет proposal для проверки/подтверждения
пользователем. before содержит только разрешённые поля; полное содержимое
документа не выдаётся модели. Валидация аргументов выполняется до формирования trace.
Журналы не сохраняют скрытые рассуждения, полный диалог или credentials.

## 6. Оптимизация и решение о кэше

Новые тесты контролируют вызовы storage, число полученных документов, серверные
filters/fields/limit и отсутствие записей при чтениях:

| Сценарий | Проверенное поведение |
|---|---|
| 21 собственный курс + зачисления | 1 запрос зачислений + 1 get_all; зачисления не перечитываются |
| Один курс | Адресное зачисление, документ курса и запрос данных этого курса |
| Одно задание по id | Адресный get задания и проверка прав; без scan коллекции |
| title=Work среди 250 посторонних заданий | Серверный equality-фильтр, проекция title/due; прочитан один подходящий документ |
| limit=2 | Не более 3 документов на группу курсов для определения следующей страницы |
| 131 задание, страница по 7 | Все страницы без дублей; максимум 8 документов на запрос группы |
| Каталог ресурсов | Реестр схемы без transaction/read/write Firestore |
| План | Не загружает description; local не вызывает предварительный get_assignments |

Это количества операций чтения данных на уровне storage; служебные begin/commit
транзакции и сетевые пакеты не включены в число «два обращения». Батч сам по себе
не уменьшает число оплачиваемых документов, проекция сама по себе уменьшает
payload, а не стоимость чтения документа. Устранение повторного запроса зачислений
уменьшает и повторные документные чтения. См. [учёт чтений Firestore](https://firebase.google.com/docs/firestore/pricing).

Постоянный JSON-кэш не добавлен: нет нагрузки/замера, который оправдывает риск
устаревших прав и расписаний, сложность invalidation и независимые cloud instances.
Остался только transaction-scoped кэш авторизации; после инструмента он удаляется.
JSON-файлы при запросах не создаются. Отдельные инструменты повторно проверяют
права и могут читать одни данные заново — это не разделяемый долговременный кэш.

Страницы query_data теперь используют серверные limit и start_after, подписанный
курсор связан с пользователем, источником, запросом и набором разрешённых курсов.
Каждая страница актуальна на свой снимок; межстраничной неизменяемости нет.
Старые offset-курсоры нужно заменить запросом первой страницы.

Особое исключение: missing legacy-поле может иметь model default. Firestore ==
не включает отсутствующее поле, поэтому для совпадающего default сохранена
ограниченная постфильтрация до 101 документа и отказ 413 при превышении, вместо
изменения семантики/неполной выдачи. Индексы course_id/student_id для трёх
коллекций подготовлены в firestore.indexes.json; файл не применялся к проекту.
Другие сочетания фильтров могут потребовать дополнительных индексов после
[проверки в выделенной среде](https://firebase.google.com/docs/firestore/query-data/indexing).

## 7. Тесты

Полный набор: **115/115 — OK**, из них 97 существовавших тестов и 18 новых.
Среда: Windows, Python 3.14.0, проектная `.venv` PyCharm. Внешние соединения
родительского процесса блокируются audit hook из scripts.check_lms.
Оригинальные suites старого демо, LMS, аутентификации и Firestore проходят.

Проверены JSON-типы/ошибки/пустые результаты, дедлайны и часовой пояс, разделение
студентов, отсутствие внутренних полей, лимиты и количество чтений, пагинация,
отзыв доступа между страницами, конфигурация test namespace и её передача MCP.
SDK-тест с настоящими Query/DocumentReference и замоканным transport проверяет
wire query: where, select, limit, start_after и физическую тестовую область.
Настоящий stdio MCP проверяет non-null structuredContent/outputSchema.
Тест Gemini использует настоящий function-calling loop и замоканный genai.Client:
проверяется объект function response и отсутствие proposal/data_access у модели.
Это не реальный вызов Gemini или облачной Firestore.

Для повторения стандартной LMS-проверки (включает новые тесты):

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.check_lms
```

Полный прогон выполнен через unittest discover('tests') с теми же переменными
pending/local/no-cloud и deny_external_connections. Локальный журнал —
`.local/optimization-all-tests.txt` (игнорируется Git).

## 8. Реальная интеграционная проверка

**Реальная облачная проверка в этой задаче не проводилась.** Подготовлен:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.check_firestore_backend --live
```

Он создаёт уникальную область system_tests/backend-<uuid>/..., поднимает временный
loopback backend, работает через прежние REST endpoints, пересоздаёт backend,
проверяет сохранённое задание через настоящий stdio MCP. Проверяются создание,
JSON-дедлайн, чтение курса/расписания, PATCH задания, пустой результат,
изолированность двух студентов, подтверждение личной задачи и сохранение после
пересоздания репозитория. Пользовательские коллекции остаются за пределами namespace.
Тестовые документы сохраняются для просмотра; удаления не выполняются.

Скрипт явно требует --live до открытия credentials/клиента. Никаких deployments,
Gemini-запросов, изменений Rules, индексов, биллинга или квот он не выполняет.
Его сценарий проверен офлайн через HTTP с MemoryStorage/direct; изоляция SDK-пути
и настоящий MCP проверены отдельно с моками. JSON-отчёт скрипта содержит только
итог и тестовую область, без токенов/ключей. Ошибка не удаляет созданные fixtures.

## 9. Оставшиеся ограничения

- Реальные credentials, IAM, требуемые индексы и сеть не проверены этими моками;
  live-сценарий остаётся отдельным шагом.
- HTTP Gemini provider по-прежнему не подключён автоматически. Function-calling
  путь подготовлен и проверен с mock client; model billing не включался.
- Авторизация, отзыв сессий и AI-счётчики остаются прежними локальными механизмами;
  для публичного cloud runtime нужны production identity и распределённые лимиты.
- Предметные списки/план по-прежнему ограничены 100 элементами. Общий scope
  ограничен 100 зачислениями; архивные legacy-записи могут потребовать явного курса.
  Обычный query_data листает коллекции больше 100 в этом scope. До четырёх групп
  курсов могут читать по limit+1 документов для одной итоговой страницы.
- Лимиты 1 МБ на данные и 24 000 символов model context сохранены.
- Поиск по title — точное equality; полнотекстовая поисковая система не добавлена.
- Между инструментами/страницами нет общего долгоживущего снимка. Курсоры
  перепроверяют scope, но изменения записей между страницами могут менять выдачу.
- Тайм-аут чтений 10 секунд, retry=None и максимум три попытки конфликта
  сохранены; begin/commit/rollback используют стандартные параметры SDK.
- Создание/изменение учебных записей остаётся преподавательским API; личное
  изменение требует подтверждения через API. Готового UI подтверждения нет.

Файлы хранения, облачные пользовательские данные и секреты не переносились.
