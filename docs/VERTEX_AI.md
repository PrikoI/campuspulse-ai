# Vertex AI в LMS

LMS использует `campuspulse.vertex_gemini`, а прежнее самостоятельное приложение
сохраняет свой провайдер. По умолчанию облачные модельные вызовы выключены.
Firestore и модель имеют отдельные настройки и могут использовать разные проекты.

```dotenv
CAMPUSPULSE_ALLOW_CLOUD=0
GOOGLE_CLOUD_PROJECT=
GOOGLE_CLOUD_LOCATION=global
CAMPUSPULSE_VERTEX_MODEL=
```

`python -m campuspulse.lms_server --check-vertex` проверяет только строки
project/location/model; не обнаруживает ADC и не обращается в сеть.
Для модельного запроса необходимы согласованная модель, доступный проект,
серверные Application Default Credentials и явное `CAMPUSPULSE_ALLOW_CLOUD=1`.
Этот режим может требовать оплачиваемый Vertex AI: не включать его автоматически.
Альтернатива без модельных расходов — `engine=local` с теми же MCP-инструментами.
`start-lms.cmd` принудительно выключает модельные облачные вызовы.

Клиент создаётся только для явно запрошенного `engine=gemini`, после проверки
сессии и доступности данных. Используются ADC, API v1, timeout 45 секунд,
одна попытка transport, максимум три модельных запроса, восемь вызовов
инструментов и 1200 выходных токенов на ответ. Синхронный SDK работает через
`asyncio.to_thread`. Сессия проверяется перед каждым модельным запросом,
дневной лимит резервируется один раз для пользовательского запроса.

Модель видит только схемы разрешённых инструментов и структурированные данные.
Подтверждение личных изменений применяется отдельным HTTP endpoint; подписанный
proposal не передаётся в модель. В trace нет текста запросов к модели или её
приватных рассуждений. Исходные модельные Content сохраняются между шагами
для function ID и thought signatures, но не публикуются в trace.

ADC и `generate_content` в тестах подменены. Реальная конфигурация проекта,
IAM, квоты и пригодность модели для Vertex AI Agent Engine ещё не проверены.
Модуль восстановлен при объединении: в коммите команды он отсутствовал.
