# Firestore в CampusPulse LMS

Интеграция использует существующий Firebase-проект `campuspulse-ai-1021`, базу
`(default)` и `firebase-admin`. Она не создаёт проект, базу, индексы, облачные
ресурсы или демонстрационные учебные записи. Существующие документы не переносились.

## Аудит исходной архитектуры

Действующий LMS запускается через `campuspulse.lms_server` на 8766. HTTP и
`lms_mcp_server` выбирают реализацию через `lms_repository.open_repository`.
`LmsRepository` описывает list/save/auth/course access, а `DataGateway` —
каталог и ограниченные именованные запросы. `TeamRepository` сохраняет эти контракты
и общий журнал; `team_gateway` остаётся точкой подключения другой реализации команды.

До этой интеграции `pending` и шаблон `team` не хранили учебных данных.
В памяти `PendingRepository` находились только временные учётные данные,
отозванные сессии и счётчики AI. Сессии подписаны HMAC, срок — восемь часов.
HTTP проверяет Host/Origin, HttpOnly cookie, роль и форму запроса; MCP получает
токен через закрытый load_session и проверяет сессию на каждом вызове.

Восемь LMS-инструментов читали данные/рассчитывали оценки и план; записей и
подтверждений со стороны LLM не было. Преподавательские POST/PATCH уже существовали.
Модели, валидация и бизнес-расчёты находятся в lms_store/lms_validation,
domain и grading. Даты с часовым поясом нормализуются в Asia/Qyzylorda.
Кэша учебных данных и действующей системы миграций не было.

Отдельное старое демо (`server`, `agent`, `tools`, `mcp_server`, порт 8765)
использует явно переданный контекст браузера, включая tasks/notes/busy.
Оно не имеет проверенной личности LMS и не получает привилегированный доступ
к Firestore. Его интерфейсы сохранены. Класс `CampusPulseAgent` для прежнего
скрипта развёртывания также остаётся контекстным; для Agent Engine нужен отдельный
вход в LMS с проверкой личности, описанный в ограничениях ниже.

## Путь данных

Обновление оптимизации: [JSON/MCP-контракты, бюджет запросов и результаты](FIRESTORE_JSON_REPORT.md).
Результаты передаются словарями/списками в памяти. `lms_json` нормализует даты,
перечисления и UUID, отклоняет NaN/Infinity, наивные datetime и неизвестные SDK-объекты.
MCP SDK публикует outputSchema и structuredContent без обёртки `result`.
Публичные ответы не переименованы в `success/data`: сохранены assignments/items/plan,
source и data_access; ошибки инструментов имеют error, status, error_code, retryable.
Gemini получает результат через Part.from_function_response как объект, без data_access
и токена proposal. API сохраняет proposal для отдельного пользовательского подтверждения.

```text
LMS HTTP / LMS agent
        → open_repository("firestore")
        → FirestoreRepository (совместимый с TeamRepository/DataGateway)
        → FirestoreStorage
        → firebase_admin.firestore → существующая Firestore

LMS agent → приватный stdio MCP → тот же open_repository и конфигурация
```

SDK и клиент создаются лениво один раз на процесс под блокировкой. Именованное
приложение `campuspulse` не переинициализирует чужое default-приложение.
При запуске репозитория выполняется одно чтение отсутствующего/служебного
`courses/campuspulse-readiness`; документ не создаётся. Успех чтения подтверждает
готовность, но не доказывает наличие учебных данных или право записи.
Ошибка SDK/сети при запуске даёт безопасный 503 без перехода к другому хранилищу.

HTTP работает в потоках. В асинхронном агенте синхронные проверки репозитория
и прямые инструменты вынесены в `asyncio.to_thread`; MCP исполняет их в отдельном
процессе/рабочем потоке FastMCP. Синхронных Firestore-запросов в event loop агента нет.

Один вызов LmsTools выполняется в единой read-only транзакции: несколько коллекций
для оценок/плана читаются согласованно. Область доступа к курсам кэшируется только
внутри этого вызова и проверяется заново на следующем. Между разными инструментами
агента данные могут измениться. Внешний академический кэш не используется.

## Коллекции и совместимость

| Путь | Назначение |
|---|---|
| `users/{uid}` | Только публичный профиль role/name и разрешённые preferences |
| `users/{uid}/tasks/{id}` | Личные задачи: title, course, due, minutes, done |
| `courses/{id}` | Существующая модель курса + закрытое серверное owner_id |
| `enrollments/{id}` | course_id, student_id, archived |
| `assignments/{id}` | Учебные задания существующего курса |
| `grade_items/{id}`, `grades/{id}` | Определения работ и оценки |
| `lessons/{id}`, `attendance/{id}` | Расписание и отметки посещаемости |
| `materials/{id}` | Извлечённые тексты, имена и ссылки материалов |

Коллекции появляются только при фактической записи. Отдельные schedules,
agent_sessions и tool_logs не создаются: расписание уже представлено lessons,
а долговременные разговоры и полные журналы не нужны текущему приложению.
JSON/SSE trace возвращается текущему авторизованному клиенту, не записывается в БД.
HTTP-журнал содержит метод/путь без тела и параметров запроса.

Публичные поля и форматы описаны в [LMS_DATABASE_CONTRACT.md](LMS_DATABASE_CONTRACT.md).
Служебный owner_id исключается из API и универсального каталога. Даты хранятся
как Timestamp и возвращаются как ISO-8601 с `+05:00`; null не заменяется вымышленной
датой или нулевой оценкой. Нативные Timestamp из существующих документов читаются.

Новые обычные учебные документы получают UUID; повторный POST без id создаёт
новую запись по прежнему контракту. PATCH всегда использует стабильный id,
проверяет объединённую запись и никогда не создаёт отсутствующий документ (404).
Для зачислений id = SHA-256 JSON-массива `(course_id, student_id)`, для оценок —
`(student_id, item_id)`, посещаемости — `(student_id, lesson_id)`.
Повторное одинаковое создание связанной записи идемпотентно; отличающееся требует
PATCH (409). Связующие ключи таких записей неизменяемы.

Транзакции проверяют владельца обоих курсов при переносе, существование студента,
зачисление, соответствие работы/занятия курсу, максимальный балл и корректность
объединённых дат. Работу/занятие с существующим id нельзя переносить в другой курс.
Максимум работы нельзя уменьшить ниже уже выставленных баллов. Учебные удаления
не добавлены в API: архивирование courses/enrollments сохраняет прежние связи.
При ошибке транзакции частичные изменения не применяются.

## Права и секреты

Admin SDK работает с серверными привилегиями и не ограничивается клиентскими
Firestore Rules. Сервер сам применяет активные зачисления, неархивные курсы и
строгий student_id для enrollments/grades/attendance. Преподаватель видит и меняет
только курсы с `owner_id == actor.user_id`; роль admin не означает глобальное
владение всеми курсами. Тело запроса не может назначить owner_id, роль или личность.
Личные пути строятся только из проверенного actor; чужой uid инструментам не передаётся.

Файл firebase-key.json исключён из Git и удалён из индекса без удаления с диска.
SDK получает путь к ключу; содержимое ключа не выводится и не передаётся в API,
аргументах MCP или frontend. В дочерний процесс передаются только нужные настройки
Firestore и серверный ключ подписи сессий. API-ключ Gemini туда не копируется.
Пользовательские поля — по allowlist; пароли, хеши паролей, токены и API-ключи
в Firestore не записываются. Не публикуйте весь environment и не упаковывайте
локальный ключ в образ/архив развёртывания.

IAM и клиентские Rules в рамках задачи не изменялись. Для будущего runtime выдайте
сервисному аккаунту только необходимый доступ к данным Firestore; не используйте
Owner/Editor и не давайте клиенту прямой серверный доступ. Разделение студентов
обеспечивает сервер, поэтому временная авторизация непригодна для публикации сервиса.

## Настройка и запуск

Подключение Firebase уже настроено; повторная настройка проекта не требуется.
Зависимость добавлена в requirements.txt; при новой установке выполните обычную
установку зависимостей в проектную `.venv`.

```powershell
$env:CAMPUSPULSE_LMS_REPOSITORY = 'firestore'
$env:CAMPUSPULSE_FIREBASE_PROJECT = 'campuspulse-ai-1021'
$env:CAMPUSPULSE_FIRESTORE_DATABASE = '(default)'
# Необязательно: по умолчанию используется существующий ключ в корне проекта.
$env:CAMPUSPULSE_FIREBASE_CREDENTIALS = (Resolve-Path .\firebase-key.json).Path
.\start-lms.cmd
```

Launcher сохраняет выбранный repository; без настройки остаётся pending.
Файлы `.env` автоматически не загружаются. Gemini, биллинг и deployment запуск
Firestore не включает. Статус: `GET /api/v1/status`; проверьте источник
`firestore:campuspulse-ai-1021/(default)` и `team_database_connected=true`.

| Переменная | Значение/назначение |
|---|---|
| `CAMPUSPULSE_LMS_REPOSITORY` | `firestore` для постоянного хранилища, по умолчанию pending |
| `CAMPUSPULSE_FIREBASE_PROJECT` | По умолчанию campuspulse-ai-1021 |
| `CAMPUSPULSE_FIRESTORE_DATABASE` | По умолчанию (default) |
| `CAMPUSPULSE_FIREBASE_CREDENTIALS` | Абсолютный путь к локальному JSON-ключу или `adc` |
| `GOOGLE_APPLICATION_CREDENTIALS` | Стандартный путь ADC, если используется локальный ADC |
| `CAMPUSPULSE_LMS_SESSION_SECRET` | Секрет HMAC; одинаковый для серверов при необходимости проверять существующие токены после перезапуска |
| `FIRESTORE_EMULATOR_HOST` | Передаётся SDK/MCP, если среда эмулятора уже настроена; эмулятор не устанавливался и не запускался |

В Google Cloud явно установите `CAMPUSPULSE_FIREBASE_CREDENTIALS=adc`, используйте
прикреплённую сервисную identity и не включайте JSON-ключ в deployment.
Поддерживаются стандартные ADC; локально без явного параметра выбирается корневой
ключ, если он существует и не определена стандартная ADC-переменная.
В распознаваемых Cloud Run/App Engine/Vertex runtime автоматического выбора
корневого ключа нет. После смены credentials/проекта перезапустите процесс.
См. [официальную настройку Admin SDK и ADC](https://firebase.google.com/docs/admin/setup).

Временные входы остаются `admin/admin`, `student1/student1`, `student2/student2`.
При первом успешном входе сохраняется только публичный профиль. Для начальной
работы студент должен хотя бы один раз войти перед зачислением. Существующий
преподавательский API создаёт курс, затем зачисление и учебные данные. Вход не
создаёт учебных записей. Создание новых учётных записей через admin/students
остаётся 503 до подключения согласованного identity provider; пароль в Firestore
ради совместимости этого endpoint не сохраняется.

## Агент, личные изменения и подтверждение

Сохранены восемь старых LMS-инструментов и их аргументы. `query_data` читает
lessons для расписания, `get_assignments` — задания/дедлайны (плюс отдельное
поле personal_tasks), `plan_study` — подготовку с учётом занятий и личных задач.
Личные задачи включаются в общий план без course_id; план конкретного курса
ограничен учебными заданиями этого курса. Завершённые личные задачи исключаются.
При локальном планировании агент использует сохранённый hours_per_day, если
пользователь не задал его явно. У прямого вызова plan_study остаётся прежнее
значение по умолчанию 3 часа; вызывающий может передать настройку явно.

Для Firestore агенту доступны два дополнительных инструмента:
`get_personal_data` и `prepare_personal_change`. Последний возвращает before/after,
подписанный proposal и `written=false`. Он не может изменить учебные задания,
оценки, зачисления, роль или owner_id. Инструмента подтверждения у модели нет.

API после входа с cookie campuspulse_lms:

1. `GET /api/v1/personal` — собственные задачи и настройки.
2. `POST /api/v1/actions/prepare` — подготовить действие для проверки:

```json
{"target":"task","payload":{"title":"Подготовиться к экзамену","due":"2030-01-01T18:00:00+05:00","minutes":120,"done":false}}
```

Для редактирования добавьте record_id и изменяемые поля payload; для удаления —
`operation:"delete"`, record_id и пустой payload. Для настройки:

```json
{"target":"preferences","payload":{"hours_per_day":2}}
```

3. Клиент показывает пользователю before/after и только после отдельного действия
пользователя отправляет `POST /api/v1/actions/confirm`:

```json
{"proposal":"полученная-подписанная-строка","confirmed":true}
```

Proposal привязан к пользователю, точному изменению, версии содержимого и десяти
минутам. Изменившаяся запись даёт 409. Повторное подтверждение без последующих
изменений идемпотентно, включая удаление; id новой задачи назначается в предложении.
Предложения не хранятся как новые документы при каждом запросе.
Frontend должен обеспечить отдельное пользовательское действие подтверждения;
автоматически подтверждать результат модели нельзя. Готового frontend здесь нет.

В local агент принимает то же изменение в поле personal_change запроса agent/query:

```json
{"message":"Добавь личное задание","personal_change":{"target":"task","payload":{"title":"Повторить тему","minutes":30}}}
```

Агент только подготовит предложение. Свободный текст local не интерпретируется
как команда записи. Gemini может выбирать эти инструменты через существующий
function-calling loop при отдельном подключении провайдера; эта задача не включает
платные вызовы и не меняет текущий запрет неподключённого провайдера HTTP.

## Квоты, ошибки и индексы

Нет listeners, polling, автозаполнения или записи журналов на каждый вызов.
SDK/клиент переиспользуется; авторизация кэшируется на один вызов инструмента.
Предметные list/план по-прежнему ограничены 100 записями; 101-я сигнализирует
превышение. Курсы при общем чтении загружаются через один get_all, зачисления
повторно используются в той же транзакции. Операция одного курса читает только
его зачисление и документ курса. Проверяются совпадение course_id/student_id,
архивирование и владение.

У query_data фильтры и проекции применяются в Firestore. Фильтр id делает
адресный get с проверкой прав, без сканирования коллекции. Для обычной страницы
каждая группа до 30 разрешённых курсов запрашивает максимум limit+1 документов;
сервер объединяет страницы по id, возвращает не более limit (1–100) и курсор.
При scope из 100 курсов возможно до четырёх групп. Отдельные страницы могут
содержать данные из коллекции больше 100 документов, но число разрешённых
курсов по-прежнему ограничено моделью доступа. Поля, не запрошенные клиентом,
не загружаются, кроме необходимых полей фильтрации/авторизации.

Подписанный курсор привязан к пользователю, запросу, источнику и текущему набору
разрешённых курсов. Каждая страница проверяет права заново; общий неизменяемый
снимок между страницами не обещается. Старые курсоры с offset после обновления
отклоняются: начните с первой страницы. Для фильтра по значению, которое модель
задаёт по умолчанию отсутствующему legacy-полю, остаётся ограниченная проверка
до 101 записи: Firestore equality не включает отсутствующие поля. При превышении
возвращается 413, а не неполный результат.

Ответ ограничен 1 МБ; AI-контекст отдельно ограничен 24 000 символов. Общий план
также ограничен 100 задачами/интервалами существующего планировщика. План читает
только нужные колонки и не требует предварительного get_assignments.
Схема list_data_resources берётся из разрешённого реестра без Firestore RPC;
connected означает подтверждённую готовность при создании репозитория, а не
периодическую проверку доступности. Ошибка реального чтения возвращается явно.

Для чтений установлены timeout=10 секунд и retry=None; SDK-транзакции допускают
до трёх попыток конфликта. Begin/commit/rollback используют стандартные RPC timeout
и retry SDK. Сетевые ошибки, quota и timeout возвращаются безопасным 503 с
журналом failed/executed=null. Источник ошибки и содержимое документов не
попадают в ответ. Автоматических бесконечных повторов приложения нет.

Нужны стандартные индексы по courses.owner_id, enrollments.student_id,
course_id и сочетаниям course_id/student_id. Если Firestore требует составной
индекс для конкретного запроса, он настраивается отдельно после проверки в
эмуляторе/тестовой среде. Подготовлен [firestore.indexes.json](../firestore.indexes.json)
для сочетаний course_id/student_id в enrollments, grades, attendance. Файл не
применялся к проекту. Произвольные разрешённые сочетания equality-фильтров могут
потребовать дополнительного индекса. Rules не менялись; 503 сообщает о такой
конфигурационной ошибке без раскрытия внутренних ссылок SDK.

Пакетное чтение уменьшает количество сетевых обращений, а проекции — объём
передачи; сами по себе они не отменяют оплату/квоту чтения каждого документа.
Повторное использование зачислений внутри транзакции также устраняет повторное
чтение тех же документов. Постоянный кэш не введён: нет замера, оправдывающего
риск устаревших расписаний и прав. Прямой доступ остаётся актуальным для каждого
нового вызова; JSON-файлы при запросах не создаются.

Бесплатная квота: 1 GiB данных, 50 000 чтений, 20 000 записей и 20 000 удалений
в день, 10 GiB исходящего трафика в месяц; учитывайте также чтения авторизации,
пустых запросов и повторы транзакций. TTL, PITR и резервные копии не включены
в бесплатную квоту и здесь не используются. Условия сверены с
[официальными квотами Firestore](https://firebase.google.com/docs/firestore/pricing).
При исчерпании квоты приложение возвращает ошибку; тариф не меняется автоматически.
Тариф/биллинг облачного проекта в рамках работы не проверялся и не изменялся.

## Миграция и тестирование

Автомиграции нет. В активном LMS раньше не было постоянных учебных записей.
Документы system_tests не являются учебными данными и не импортируются.
Если в существующей Firestore уже есть другая схема, сначала согласуйте отображение:
старым курсам нужен owner_id, связанным записям — описанные детерминированные id,
пользователям — публичная роль. Некорректные документы не исправляются незаметно;
чужие поля не выдаются через каталог. Архивные SQL и данные браузерного демо
автоматически не переносятся.

Офлайн-проверки LMS и Firestore:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.check_lms
# Только адаптер:
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p test_lms_firestore.py -v
```

Тесты используют инъекцию тестового transactional storage и моки firebase-admin.
SDK-тест проверяет настоящую сериализацию Timestamp/set/delete с замоканным
transport. MCP-тест запускает настоящий stdio-процесс с FirestoreRepository и
тестовым storage. Пересоздание репозитория проверяет чтение из того же backing
storage; это не заявление о проведённом тесте настоящей облачной перезагрузки.
В scripts.check_lms внешние соединения родительского процесса блокируются.
Ключи не читаются. Отдельно проверяются изоляция, права преподавателя, ошибки,
отсутствующие документы, повторные и конкурентные записи и user confirmation.

`test_firebase.py` больше не обращается к облаку при импорте/сборе тестов.
Ручной `python test_firebase.py --live` пишет новый уникальный документ только
в system_tests, читает его и оставляет для проверки; существующие документы не
перезаписывает и не удаляет. Этот live-тест в рамках интеграции не выполнялся.

Подготовлена более полная проверка через существующие REST и MCP:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.check_firestore_backend --live
```

Она поднимает временный loopback backend, создаёт только тестовые профили,
курс, зачисление, задание, занятие и личную задачу внутри уникальной области
`system_tests/backend-<32 hex>/...`. Область валидируется, передаётся в MCP через
серверную CAMPUSPULSE_FIRESTORE_TEST_NAMESPACE и указывается в source.
Проверяются JSON, дедлайн, расписание, изменение задания, изоляция двух студентов,
подтверждение личной задачи и чтение после пересоздания репозитория через настоящий MCP.
Fixture-документы остаются для проверки; пользовательские коллекции не изменяются.
Без --live скрипт завершится до открытия credentials/соединения. В тестах сам
сценарий проверен только с MemoryStorage и direct-транспортом, а MCP отдельно —
с mock storage. Настоящая облачная проверка этим скриптом пока не выполнялась.

## До Vertex AI Agent Engine

Нужно заменить временные логины проверенной identity provider, привязать реальные
uid к профилям/владению курсами, сделать общий отзыв сессий и атомарные общие AI
бюджеты (сейчас они унаследованы в памяти). Постоянный session secret сам по себе
не решает распределённый logout. После перезапуска приложения учебные и личные
данные сохраняются; при новом случайном session secret потребуется повторный вход.

Нужен frontend с отдельным экраном подтверждения и same-origin proxy, отдельный
согласованный запуск Gemini-провайдера, cloud wrapper для LMS с проверенной
личностью вместо контекстного CampusPulseAgent, IAM с минимальными привилегиями,
проверка индексов и транзакций в эмуляторе/выделенных облачных данных, нагрузочные
проверки квот, упаковка без секретного JSON и отдельное согласование расходов
Agent Engine. Deployment в этой задаче не выполнялся.
