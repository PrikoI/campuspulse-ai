# Переходник базы команды → CampusPulse LMS

Реализация Firestore доступна через `CAMPUSPULSE_LMS_REPOSITORY=firestore`:
[архитектура и запуск](FIRESTORE.md). Контракт ниже сохранён для совместимости.
Описание неподключённого шаблона относится к режиму `team`; Firestore реализует
чтение/учебные записи с проверкой владельца и отдельные личные изменения.

**Для разработчика базы:** [DATABASE_QUICKSTART.md](DATABASE_QUICKSTART.md) и
[`campuspulse/team_gateway.py`](../campuspulse/team_gateway.py). Универсальный шлюз
объявляет любые разрешённые ресурсы базы через describe и читает их через query.
Он не ограничен восемью сущностями ниже: они нужны для предметных LMS-расчётов.

Обёртка [`campuspulse/lms_team_adapter.py`](../campuspulse/lms_team_adapter.py)
связывает шлюз с API/MCP. Её можно выбрать
уже сейчас: `CAMPUSPULSE_LMS_REPOSITORY=team`. Пока методы не реализованы,
он честно сообщает `source=team-unconfigured`, `team_database_connected=false`,
возвращает 503 и журнал попытки. Драйвера, соединения, собственных таблиц,
SQLite, миграций, seed или учебных записей в шаблоне нет.

Технологию и реальную схему базы выбирает участник команды. Внешние имена полей
могут отличаться: адаптер переводит их в контракт ниже. API, MCP и агент работают
с этим общим форматом. `domain.py` содержит планировщик и проверку временных
интервалов; доступ к базе туда добавлять не нужно.

Для универсального каталога и query_data поля ниже не обязательны; их схема
поступает от самого шлюза. Таблица нужна для стандартных коллекций LMS и расчётов.

## Что передать разработчику базы

Нужно согласовать технологию/драйвер, параметры доступа, реальные названия полей,
идентификаторы пользователей и курсов, связи и индексы, часовые пояса, правила
доступа преподавателей, веса из силлабуса и ограничения размера выдачи.
Пароли подключения передаются безопасным способом вне исходников и чата.
Не требуется копировать чужую физическую схему: достаточно обеспечить отображение
в следующие сущности и отношения.

### Сущности

Каждая запись в ответе `list`/`save` содержит стабильный строковый `id` (до 120
символов). ID уникален внутри коллекции. В API IDs непрозрачны: из названия курса
или имени человека их не вычислять. Все поля в колонке «формат ответа» должны
присутствовать после отображения адаптером. Значения по умолчанию ниже — правила
формата, а не генерация академических данных.

| Коллекция | Обязательные поля POST | Формат ответа и семантика остальных полей |
|---|---|---|
| `courses` | code, name | id, code, name, policy (объект политики), archived (boolean; при создании false) |
| `enrollments` | course_id, student_id | id, course_id, student_id, archived (boolean; при создании false) |
| `assignments` | course_id, title | id, course_id, title, description (строка, по умолчанию пустая), due (ISO timestamp или null), minutes (целое 10–2400 или null), week (целое 1–100 или null) |
| `grade_items` | course_id, title, component | id, course_id, title, component, max_score (число >0, по умолчанию 100 только для процентной шкалы), weight (положительный относительный вес, по умолчанию 1 для равных работ), week (целое или null) |
| `grades` | course_id, student_id, item_id, score | id, course_id, student_id, item_id, score (число в шкале grade_item или null), comment (строка, по умолчанию пустая) |
| `lessons` | course_id, title, starts_at, ends_at | id, course_id, title, starts_at, ends_at, kind (строка; по умолчанию пустая, если тип не указан) |
| `attendance` | course_id, student_id, lesson_id, status | id, course_id, student_id, lesson_id, status |
| `materials` | course_id, name, text | id, course_id, name, text, week (целое или null), source_url (http/https или пустая строка) |

Разрешённые поля запросов — `FIELDS` в `lms_store.py`, обязательные — `REQUIRED`
в `lms_validation.py`. `id` назначается базой/адаптером и не принимается в теле
POST/PATCH. PATCH содержит непустой набор изменяемых полей. Неизвестные поля,
включая смену роли, отклоняются. Создание студента — отдельный endpoint, тело
`{username,password,name}`; клиент не выбирает роль.

У courses/enrollments архивирование сохраняет связи и исключает запись из активного
доступа студента. Для остальных коллекций удаления в текущем API нет. Создание
или изменение связей требует проверки существования всех связанных сущностей.

**Критические связи и уникальность:**

- enrollments: уникальная пара `(course_id, student_id)`; обе сущности существуют.
- grade_items/assignments/lessons/materials принадлежат существующему курсу.
- grades: уникальная пара `(student_id, item_id)`; курс item совпадает с course_id;
  студент зачислен на этот курс; score между 0 и max_score конкретного item.
- attendance: уникальная пара `(student_id, lesson_id)`; курс lesson совпадает с
  course_id; студент зачислен на курс; status — present, absent, late или excused.
- PATCH проверяет объединённую запись, а не только новые поля, и не создаёт запись
  при отсутствии указанного id. Уникальность и проверки связей защищаются
  транзакцией/ограничениями базы, включая параллельные запросы.

Для чтения нужны индексы по active enrollments студента, данным курса и
парам student/item и student/lesson. Нужны также правила владения курсами
преподавателями: поле/связь определяется реальной схемой команды; не считать
любого будущего преподавателя глобальным администратором.

### Неизвестные данные и даты

`null`/отсутствующая оценка — неизвестное значение, а не ноль. Отсутствие attendance
не означает absent. Неизвестный due или minutes не заполняется примером/оценкой
модели. Планировщик пропускает задания без minutes и явно возвращает их ID в
`assignments_without_effort`. Задания без due имеют отдельную причину в плане.

Даты входа должны иметь часовой пояс. В ответах нормализовать `due`, `starts_at`,
`ends_at` в ISO-8601 с единым `+05:00` (`Asia/Qyzylorda`), например через
`domain.parse_time(value).isoformat()`. Это необходимо для текущих сравнений
посещаемости. Конец занятия позже начала; при PATCH сравнивать после объединения
с уже сохранёнными значениями. Сама база может хранить UTC/native Timestamp.

`component`: `regmid`, `midterm`, `regend`, `endterm`, `attestation1`,
`attestation2`, `final`. Нужно подтвердить отображение реальных итогов периода
команды в attestation1/2. Если переданы итоговые аттестации, они имеют приоритет
над попыткой собрать их из coursework/exam.
`policy` нормализуется через `grading.policy_config`. Встроенная политика имеет
источник AITU 2025, но веса coursework/exam остаются null до получения силлабуса.
Нельзя выдавать стандартное равенство относительных весов работ за проверенное
правило конкретного курса. Если система команды не знает весов, отметьте данные
неполными и не отдавайте расчёт с выдуманным policy. Изменение базовых порогов
и формулы требует подтверждённого основания.

Материалы возвращаются как извлечённый текст до 50 000 символов и имя до 200
символов (поисковая подпись сейчас ограничивается 150). Разбиение страниц
`[Страница N]` сохранять в тексте. URL источника не загружается автоматически.
Загрузку файлов/Storage и их извлечение подключают отдельно; не подставлять URL
вместо текста материала.

## Методы переходника

Формальный интерфейс: `LmsRepository` в [`lms_store.py`](../campuspulse/lms_store.py).
`Principal(user_id,role,name)` передаётся сервером после проверки сессии. Нельзя
доверять user_id/role из клиентского тела.

| Метод | Обязанность реализации |
|---|---|
| `list(kind, actor, course_id=None, audit=None) -> list[dict]` | Читать с фильтрацией прав на стороне сервера/базы; нормализовать поля; добавить журнал фактического доступа в переданный список audit |
| `save(kind, actor, payload, record_id=None) -> dict` | Только преподаватель с правом на курс; None означает создание, иначе частичное обновление; общая валидация и транзакционные связи/уникальность |
| `users(actor) -> list[dict]` | Разрешённые преподавателю пользователи; только публичные id/role/name, никаких password/hash/token |
| `create_student(actor,payload) -> dict` | Управляемое создание через согласованную авторизацию; вернуть публичную личность |
| `allowed_courses(actor) -> set[str]` | Доступные активные курсы студента/преподавателя |
| `check_course(actor,course_id)` | Отказ 403/404 до выдачи данных при отсутствии доступа/курса |
| `require_admin(actor)` | Проверка преподавательской роли; она не заменяет проверку владения курсом |
| `data_resources(actor) -> dict` | Каталог разрешённых данных всей базы, делегируется DataGateway.describe |
| `query_data(actor,request) -> dict` | Запрос по имени и схеме ресурса, делегируется DataGateway.query |
| `login(username,password) -> (token,Principal)` | Временная локальная реализация наследуется; production заменяет её |
| `principal(token) -> Principal` | Проверять подпись/срок/отзыв и соответствие пользователю команды |
| `logout(token)` | Отзывать доступ; для production нужен общий отзыв между процессами |
| `reserve_model_query(actor,maximum=10)` | Ограничение запросов; в production — общий атомарный счётчик, не только память процесса |
| `mcp_environment() -> dict[str,str]` | Передать MCP дочернему процессу выбор ТОГО ЖЕ адаптера и только нужные секретные параметры доступа |

`source` — честное непустое имя реального источника. `team_database_connected`
может стать true только после успешной реальной проверки готовности, не просто
после наличия URL в окружении. Недоступность уже настроенной базы тоже должна
приводить к 503, без резервной SQLite, списка [] или подмены данными.

**Доступ студента:** все списки фильтруются по активным зачислениям и неархивным
курсам. В grades/attendance/enrollments дополнительно строго собственный student_id.
Переданный course_id сужает доступ, а не расширяет его. Никогда не загрузить всех
студентов с последующей фильтрацией только в браузере/модели. Проверки обязательны
внутри адаптера для каждого метода; агент не является границей доступа.

Результат `list` ограничивать максимум 100 записями и общим размером ответа,
материалы — отдельно. Если объём больше поддерживаемого, вернуть явную ошибку
с просьбой уточнить курс; молча обрезать записи нельзя. Pagination пока не
поддерживается текущим HTTP-контрактом. Лимит AI-контекста — 24 000 символов
на результат инструмента; инструменты могут дополнительно отказать в слишком
большом ответе. Межколлекционные расчёты требуют согласованного снимка/проверки
версий при конкурентном обновлении; это ещё предстоит реализовать с выбранной БД.

## Журнал и ошибки

Используйте `LmsError(message,status)` с безопасным текстом. 400 — неверный
вход, 401 — сессия, 403 — права, 404 — запись, 409 — конфликт уникальности,
503 — нет подключения. На ошибку можно добавить `error.data_access` со списком
событий фактических попыток. Пароли/SQL/connection strings/текст материалов/токены
в ошибки и журнал не помещать.

Событие содержит `type=database_request`, `operation`, `collection`, `filters`,
`source`, `status`, `executed`, `rows`, `at`. До исполнения: not_connected,
executed=false, rows=null. После реального чтения: status=ok, executed=true,
rows — число возвращённых записей. Это число не нужно вычислять по выдуманному
набору. Ошибки исполнения отделяются от запретов доступа; описывайте только
реально выполненные действия, включая корректно пустой результат подключённой БД.
Список audit нужно пополнять, а не заменять, чтобы сохранять предыдущие чтения.

## Как подключить

1. Участник создаёт реальную базу в согласованной среде и передаёт схему/доступы.
   Этот репозиторий сейчас не создаёт ему базу или облачные ресурсы.
2. Реализовать TODO в `TeamRepository`. Подключение/готовность добавить в его
   конструктор или отдельную явную проверку. Секреты держать вне исходников.
3. Реализовать реальные методы чтения/изменения, отображение полей, проверки
   прав и журнал. Входные структурные проверки можно переиспользовать из
   `lms_validation.py`, они не заменяют проверки связей в базе.
4. В `mcp_environment()` явно перечислить необходимые настройки командной БД.
   HTTP и MCP создают разные экземпляры адаптера: память и соединения процесса
   не разделяются. Оба должны попадать в один источник и одинаково проверять
   личность. Внешние API-ключи модели дочернему процессу не передаются.
5. Проверить локальный API с реальными разрешёнными данными команды, изоляцию
   двух пользователей, владение курсами и конкурентные записи. До появления
   базы проверяются только честные отказы и контракт; фикстуры не создаются.

Фабрика `lms_repository.open_repository()` уже знает имя `team`; менять сервер,
агента и MCP для выбора этого адаптера не нужно. Параметры `path` и `seed_demo`
запрещены; аргумент bootstrap сохранён для совместимости и не разрешает создавать
данные. `start-lms.cmd` использует pending по умолчанию и сохраняет выбранный
repository; также можно использовать явный запуск:

```powershell
$env:CAMPUSPULSE_LMS_REPOSITORY = 'team'
$env:CAMPUSPULSE_ALLOW_CLOUD = '0'
$env:CAMPUSPULSE_MODE = 'local'
.\.venv\Scripts\python.exe -X utf8 -m campuspulse.lms_server --port 8766
```

До реализации это запустит **неподключённый шаблон**, а не работающую базу.
`GET /api/v1/status` покажет team-unconfigured/false; чтение — 503.
Даже после подключения базы провайдер Gemini, Vertex AI/ADK/Agent Engine и
корпоративная авторизация требуют отдельной интеграции и согласования расходов.
