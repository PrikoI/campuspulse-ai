## Что действительно есть в новом бэкенде

- `campuspulse/lms_server.py`: отдельный локальный HTTP API `/api/v1`, порт по умолчанию **8766**, привязка к 127.0.0.1. Корень возвращает JSON с описанием сервиса, готового нового сайта там нет. Сервер использует стандартную библиотеку Python, не FastAPI.
- `lms_pending.py`: **нет подключения к базе и учебных наборов данных**. В памяти находятся временные учётные данные, подписанные сессии и счётчики запросов. Входы `admin/admin`, `student1/student1`, `student2/student2`. Это сессии для разработки, а не корпоративная авторизация.
- `lms_store.py`: Protocol `LmsRepository`, роли, перечень коллекций/полей, ошибки и вспомогательная валидация. Активного SQL-адаптера в нём нет.
- `lms_repository.py`: единая фабрика API и MCP; провайдеры pending и неподключённый/будущий team. Неизвестные провайдеры, локальные файлы БД и заполнение демонстрационными записями отклоняются. SQLite-реализация и её старые тесты архивированы как `.txt` в `build/archive-unused`, не импортируются и не должны запускаться.
- `lms_tools.py`: шесть инструментов — `get_courses`, `get_assignments`, `get_grades`, `get_attendance`, `read_materials`, `plan_study`. Их учебные операции сейчас возвращают отсутствие подключения. Код обработки будущих записей есть, интеграция с базой команды не проверена.
- `lms_mcp_server.py`: настоящий отдельный stdio MCP-процесс FastMCP. Внутренний `load_session` передаёт проверенную сессию; этот инструмент не передаётся модели. Идентичность берётся из сессии, не из аргумента student_id.
- `lms_agent.py`: MCP-вызовы, журнал и SSE; локальный маршрутизатор запросов и ветка Gemini function calling. По умолчанию `engine=local`: это **не ответ LLM**. При неподключённой базе Gemini блокируется до создания клиента и расходования квоты. Полный живой цикл Gemini → данные LMS → ответ не подтверждён.
- `grading.py`: независимая арифметика оценок, без запросов к модели и базе. Пустые оценки остаются неизвестными. Учтены рейтинг допуска, минимальные пороги, целевой итог и необходимый финальный балл.
- `agent.py`: общий цикл Gemini ограничен по шагам, вызовам и длине ответа; тайм-аут 45 секунд, автоматические повторы SDK отключены. LMS задаёт 3 модельных шага, 8 вызовов инструментов, 1200 выходных токенов. Счётчики текущего адаптера — 10 запросов на пользователя и 20 суммарно в день в памяти; это не гарантированный денежный лимит и после перезапуска сбрасывается.
- HTTP-проверки Host/Origin, HttpOnly/SameSite cookie, запрет студенту административных действий, запрет выбирать чужую идентичность, ограничение размера запроса и параллельности.

Сейчас операции с академическими данными намеренно отвечают 503. Событие имеет `type=database_request`, `status=not_connected`, `executed=false`, `rows=null`. Это **попытка**, а не результат чтения. Для локального чата HTTP-ответ может быть 200 с журналом ошибки инструмента; SSE после начала потока сообщает ошибки событиями.

## Основные маршруты

- `GET /api/v1/status` — доступен без входа.
- `POST /api/v1/auth/login` — JSON `{"username":"admin","password":"admin"}`; ответ устанавливает cookie `campuspulse_lms`.
- `GET /api/v1/me`; `POST /api/v1/auth/logout` с JSON `{}`.
- Студенческие `GET /api/v1/{collection}`; коллекции: courses, enrollments, assignments, grade_items, grades, lessons, attendance, materials. Необязательный `course_id`, никаких клиентских student_id.
- `GET /api/v1/grade-summary?course_id=...&target=70`; `GET /api/v1/attendance-summary?course_id=...`.
- Админ: `GET /api/v1/admin/users`, `POST /api/v1/admin/students`, `GET/POST /api/v1/admin/{collection}`, `PATCH /api/v1/admin/{collection}/{id}`. Сейчас работа с данными возвращает 503, а не сохраняет записи.
- `POST /api/v1/agent/query` или `/api/v1/agent/stream`: например `{"message":"Покажи оценки","course_id":"course-id","page":"grades","engine":"local"}`. Stream — POST с SSE, поэтому обычный браузерный EventSource для него не подходит; понадобится fetch с чтением потока.
- `POST /api/v1/grading/calculate` после входа: `{"items":[{"component":"attestation1","score":82},{"component":"attestation2","score":74}],"target":70}`. Результат: register=78, required_final=58. Это явно помеченный расчёт по введённым числам (`simulation=true`, `database_accessed=false`), не оценки из LMS и не запись в ведомость.

Вызовы из будущего фронтенда нужно интегрировать отдельно: текущий сервер разрешает только свой локальный Origin. Нельзя просто открыть произвольный фронтенд на другом порту и ожидать, что CORS/cookie уже настроены. Предпочтителен согласованный same-origin proxy; промышленный сервер/HTTPS и авторизация ещё требуют работы.
